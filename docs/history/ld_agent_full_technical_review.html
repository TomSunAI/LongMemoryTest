2. LD-Agent 核心思路

LD-Agent 的目标是长期、多 session、开放域对话。它认为长期陪伴式对话不能只依赖当前上下文， 还需要同时维护两类内部知识：

  • 事件记忆：过去发生过什么，尤其是跨 session 仍有用的高层事件摘要。
  • Persona 记忆：用户和 agent 分别呈现出的稳定个人特征。

论文把 LD-Agent 描述成 model-agnostic 框架：event perception、persona extraction、response generation 三个模块可以独立训练、独立替换、独立调参。官方实现则主要围绕 ChatGLM3-6B + LoRA 和 ChatGPT API 展开实验。

输入侧问题

当前 user utterance 往往只暴露局部语义，缺少此前 session 的事件线和稳定画像。

multi-session long-term dialogue personalization

LD 的解决方式

从历史中抽 event summary 和 persona traits，在当前生成前检索并拼入 prompt。

event memory persona memory retrieval-augmented generation

4. Event Memory 模块

源码入口：/private/tmp/LD-Agent/Module/EventMemory.py。这是 LD-Agent 里最重要的记忆模块， 覆盖短期上下文、session 切换、长期事件摘要、ChromaDB 写入、topic retrieval 和时间衰减。

4.1 初始化：依赖与状态

字段 / 依赖 源码行为 作用
DefaultEmbeddingFunction() ChromaDB 默认 embedding function。 用于 collection query 的底层向量候选召回。
ImageLoader() 初始化 data loader，虽然主实验基本使用 text。 保留 image datatype 支持。
spacy.load("en_core_web_sm") 加载英文 spaCy 模型。 抽取 noun lemma 作为 topic tokens。
chromadb.Client() 无 memory_cache 时使用内存 client。 单次评测样本的临时 memory bank。
chromadb.PersistentClient(path=...) 有 memory_cache 时持久化。 复用已存 memory。
short_term_memory = [] 当前 session 内的短期 turn 列表。 给 generator 提供 recent context，并在 session boundary 时被总结。

4.2 Short-term event memory 到底是什么

LD-Agent 的 short-term event memory 不是向量库，也不是 summary，而是当前 session 里还没有被压缩的原始对话 turn 缓冲区。 源码里就是一个 Python list：self.short_term_memory = []。 

short_term_memory = [
  {"idx": 0, "time": t0, "dialog": "SPEAKER_1: ..."},
  {"idx": 1, "time": t0, "dialog": "SPEAKER_2: ..."},
  {"idx": 2, "time": t1, "dialog": "SPEAKER_1: ..."},
  {"idx": 3, "time": t1, "dialog": "SPEAKER_2: ..."}
]

4.2.1 它保存什么

字段 含义 来源
idx 当前 short-term list 中的顺序编号。 追加时用 len(short_term_memory)。
time 当前 turn 的时间戳，用于判断是否跨 session。 time.time() + current_time_pass。
dialog 一条原始发言文本，带 speaker 前缀。 user query 由 context_retrieve() 写；gold agent response 由 MSC.py 手动 append。

4.2.2 它什么时候写入

每个 user utterance 到来时，MSC 会先调用：

context_memories = memory_bank.context_retrieve(
  dial["SPEAKER_1"],
  n_results=context_memory_number,
  current_time=current_time,
  datatype="text"
)

context_retrieve() 会把当前 user query 写进 short_term_memory。 随后，MSC 会把数据集里的 gold SPEAKER_2 response 也写入同一个 list： 

response_data = {
  "idx": len(memory_bank.short_term_memory),
  "time": current_time,
  "dialog": "SPEAKER_2: {gold_response}"
}
memory_bank.short_term_memory.append(response_data)
实验细节： 在 LD 的 MSC 离线评测里，short-term memory 里保存的是 ground-truth 历史对话，不是模型自己生成的历史。 这保证后续评测时，memory bank 建立在真实历史上。

4.2.3 它怎么 retrieval

short-term memory 的 retrieval 很简单，不走 Chroma，不算 embedding，不算 overlap。它就是取当前 session 中最近的 n_results 条： 

if len(short_term_memory) >= n_results:
  return short_term_memory[-n_results:]
else:
  return short_term_memory

默认 context_memory_number=30，所以 LD generator 可以看到当前 session 最近最多 30 条 short-term context。 这些内容之后会被格式化成： 

[TURN 0] : SPEAKER_1: ...
[TURN 1] : SPEAKER_2: ...
In this turn, SPEAKER_1 said: current user query.

4.2.4 它什么时候消失

short-term memory 是临时缓冲。只要 context_retrieve() 判断当前 user query 和上一条 short-term memory 的时间间隔超过 1 小时，上一 session 的 short-term memory 就会被 summary、写入 long-term event memory，然后被清空： 

if current_time - short_term_memory[-1]["time"] > 3600:
  summarize previous short_term_memory
  store summary as long-term event memory
  short_term_memory = []
  append current user query as new session start

4.3 Long-term event memory 到底是什么

long-term event memory 是上一 session 的压缩事件摘要。它不是完整聊天记录，也不是 persona。 它的最小单位是“一个 session 被总结后得到的一条 event memory”。

4.3.1 它从哪里来

long-term event memory 来自被 flush 的 short-term memory。当 LD 判断进入新 session 时，会把上一 session 的所有 short-term turns 拼成如下文本： 

(line 1) SPEAKER_1: ...
(line 2) SPEAKER_2: ...
(line 3) SPEAKER_1: ...
(line 4) SPEAKER_2: ...

这段文本进入 context_summarize()，产出一条 20 words 以内的事件摘要。 这条摘要连同 topics、time、idx 等 metadata 一起写入 ChromaDB collection。

4.3.2 它保存什么

long-term event memory 的 metadata 是固定结构：

{
  "idx": collection.count(),
  "dialog": "",
  "time": last_short_term_turn_time,
  "topics": "noun1,noun2,...",
  "datatype": "text",
  "summary": "brief event summary"
}

其中 summary 是以后展示给 generator 的内容； topics 是以后计算 overlap 的内容； time 是以后计算 time decay 的内容。

4.3.3 它怎么 retrieval

long-term event memory 的 retrieval 由 relevance_retrieve() 完成。它不是简单取最近， 而是用当前 user query 去 ChromaDB 找候选，再用 topic overlap 和 time decay 选出最相关的一条或若干条。 

current user query
  ↓
spaCy noun lemma extraction
  ↓
ChromaDB query candidates
  ↓
compute topic overlap with memory["topics"]
  ↓
multiply by exp(-decay_temp * time_gap)
  ↓
return best event memory metadata

4.4 Summary / Storage / Retrieval 三步完整解释

4.4.1 Summary：什么时候总结，输入是什么，输出是什么

问题 LD 源码答案
什么时候 summary？ 当前 user query 到来时，如果距离上一条 short-term memory 超过 1 小时，就总结上一 session。
summary 的输入是什么？ 上一 session 的 short-term memory，格式化成 (line n) speaker: text。
summary 用哪个模型？ 调用 LLMclient.employ(..., "EventSummary")。ChatGLM3 路线会切换到 summarizer LoRA；ChatGPT 路线只按 prompt 调 API。
summary 的输出是什么？ 一条英文短事件摘要，prompt 要求 within 20 words。
summary 写到哪里？ 写入 long-term event memory metadata 的 summary 字段。

4.4.2 Storage：短期和长期分别怎么存

记忆类型 存储位置 存储内容 生命周期
Short-term event memory self.short_term_memory Python list 当前 session 原始 user / gold agent turns：idx、time、dialog。 跨 session 后被 summary，然后清空。
Long-term event memory ChromaDB collection document 是 noun topics 字符串；metadata 包含 summary、topics、time、idx 等。 跨 session 保留；后续 user query 可检索。

长期写入时源码调用： 

self.store(
  self.collection.count(),
  merged_nouns_str,
  MetaData(
    idx=self.collection.count(),
    dialog="",
    time=self.short_term_memory[-1]["time"],
    topics=merged_nouns_str,
    datatype="text",
    summary=last_session_summary
  ).to_dict(),
  datatype="text"
)

store() 的 text 分支最终执行： 

collection.add(
  ids=[str(id)],
  documents=[merged_nouns_str],
  metadatas=metadata
)

4.4.3 Retrieval：短期和长期分别怎么取

记忆类型 retrieval 函数 检索逻辑 输出给 generator 的形式
Short-term event memory context_retrieve() 取当前 session 最近 n_results 条原始 turns。 [TURN idx] : speaker: text 组成 recent context。
Long-term event memory relevance_retrieve() 当前 query 抽 noun topics；Chroma 召回候选；计算 overlap 和 time decay；返回 best memory metadata。 {past_time} ago, {summary}. 组成 relevant memory。

4.4.4 一轮完整流程示例

Session 1:
  user_1 arrives
    context_retrieve appends SPEAKER_1:user_1 into short_term_memory
    relevance_retrieve finds no long-term memory
    MSC appends gold SPEAKER_2 response
  user_2 arrives
    context_retrieve appends SPEAKER_1:user_2
    relevance_retrieve still queries existing long-term memory
    MSC appends gold SPEAKER_2 response

Session 2 starts after time gap:
  new user arrives
    context_retrieve detects > 1 hour gap
    previous short_term_memory is summarized
    summary + topics are stored as long-term event memory in ChromaDB
    short_term_memory is cleared
    current user becomes first short-term item of new session
    relevance_retrieve can now retrieve previous session summary

4.5 Memory metadata

LD 长期 event memory 的 metadata 类是 MetaData，字段固定为：

{
  "idx": int,
  "dialog": str,
  "time": float,
  "datatype": "text" | "image",
  "summary": str,
  "topics": "noun1,noun2,..."
}

其中 summary 是 session summary；topics 是从 session 原文抽取的 noun lemma 集合； time 用于 time decay；idx 是 collection 中的顺序编号。

4.6 store()：写入 collection

store(ids, key, metadata, datatype="text") 是底层写入函数。若 datatype 是 text， 源码调用 collection.add(ids=..., documents=key, metadatas=metadata)。

容易忽略的细节： 在 session summary 写入处，key 传入的是 merged_nouns_str，即 topic nouns 字符串； summary 放在 metadata 里。因此官方默认 Chroma document 更像 topic key，而不是自然语言 summary。

4.7 context_retrieve()：短期记忆与 session boundary

该函数同时做三件事：

  1. 判断是否跨 session。
  2. 如果跨 session，把上一 session 总结并写入长期 event memory。
  3. 把当前 user query 写入新的或现有的 short-term memory。
if short_term_memory not empty
and current_time - last_short_term_time > one_hour_seconds:
  summarize previous short_term_memory
  extract noun topics from previous session context
  store summary + topics into ChromaDB
  clear short_term_memory
  append current user query as first item
else:
  append current user query into short_term_memory

返回值是当前 short-term memory 的最后 n_results 条。默认 context_memory_number=30，所以 generator 通常能看到当前 session 的较长上下文。

4.8 context_summarize()：事件摘要 prompt

LD 的 summary prompt 非常直接：

System:
You are good at extracting events and summarizing them in brief sentences.
You will be shown a conversation between {usr_name} and {agent_name}.

User:
#Conversation#:
{context}.
Based on the Conversation, please summarize the main points of the conversation
with brief sentences in English, within 20 words.
SUMMARY:

官方训练里 EventSummary 可使用 LoRA 后的 summarizer；如果 summary_model=default， 则使用原始 ChatGLM3 或 ChatGPT。

4.9 relevance_retrieve()：长期记忆检索

这是 LD-Agent memory retrieval 的关键函数。

第一步：query topic extraction

tokenized_item = spacy_model(query_item)
query_nouns_item = unique lemma tokens where POS == "NOUN"
query = ",".join(query_nouns_item)

默认 ori_mem_query=False，所以 Chroma 的 query text 不是原始用户句子，而是 noun lemma 字符串。

第二步：Chroma 候选召回

text 分支调用 collection.query(query_texts=query, n_results=n_results)。 默认 relevance_memory_number=1，即只期望拿 1 条相关长期 event memory。

第三步：overlap + time decay 重排

overlap_count = |query_nouns ∩ retrieved_topics|

if query_nouns or retrieved_topics empty:
  overlap_score = 0
else:
  overlap_score =
    0.5 * overlap_count / len(query_nouns)
    + 0.5 * overlap_count / len(retrieved_topics)

time_decay = exp(-decay_temp * time_gap)
overall_score = time_decay * overlap_score

源码默认选择 overall_score 最高且 overlap_count > 0 的 best memory。 没有合适记忆时返回空列表，调用方再渲染为 No relevant Memories.。

ori_mem_query=True 分支

如果开启 ori_mem_query，query 不再替换为 noun topics，而是使用原始 query。 此时源码会比较 Chroma distance 和 dist_thres，更接近语义相似度检索。 但官方默认参数是 ori_mem_query=False。

4.10 direct_retrieve() 与 retrieve()

函数 作用 实验主链路是否使用
direct_retrieve() 直接用原始 query 检索，并按 distance < threshold 过滤。 MSC 主链路未直接调用。
retrieve() Chroma collection query 的薄封装，返回原始 results。 不是 MSC 主链路核心。

5. Persona 模块

源码入口：/private/tmp/LD-Agent/Module/Personas.py。该模块维护两个 list： user_traits 和 agent_traits。

5.1 traits_update(inquiry, response) 的顺序

user_traits_update(inquiry)
merged_user_traits = all or latest max_user_personas
merged_agent_traits = all or latest max_agent_personas
agent_traits_update(response)
return merged_user_traits, merged_agent_traits
时机细节： 当前 user inquiry 抽出的 user trait 可以进入当前轮返回的 merged_user_traits； 当前 agent response 抽出的 agent trait 不会进入当前轮 merged_agent_traits，只能影响后续轮。

5.2 Persona extraction prompt

user 和 agent 使用同一套 prompt 模板。核心规则是：如果句子里没有可抽取 trait，返回 NO_TRAIT。

System:
You excel at extracting user personal traits from their words,
a renowned local communication expert.

User:
If no traits can be extracted in the sentence, you should reply 'NO_TRAIT'.
... examples ...
Please extract the personal traits who said this sentence
(no more than 20 words):
{sentence}

5.3 Trait 过滤规则

源码规则很简单：

  • 如果输出包含 NO_TRAIT，不写入。
  • 如果输出长度不超过 3，不写入。
  • 否则 append 到对应 traits list。

5.4 max_user_personas / max_agent_personas

配置默认值是 0。源码逻辑是： 

if len(traits) <= max_personas:
  use all traits
else:
  use traits[-max_personas:]

当 max_personas=0 且已有 traits 时，Python 的 traits[-0:] 等价于 traits[0:]，实际会使用全部 traits。因此默认值 0 在源码里不是“禁用 persona”，而更接近“不过滤”。

7. Clients 与模型调用

源码入口：/private/tmp/LD-Agent/Module/Clients.py。

7.1 GPTClient

  • 使用 OpenAI Python SDK。
  • 请求格式是 system + user 两条 message。
  • 记录 completion tokens、prompt tokens、total tokens。
  • 模块名如 EventSummary、PersonaExtraction、ResponseGenerator 只用于日志统计。

7.2 GLMClient

  • 加载 AutoModelForCausalLM.from_pretrained(..., trust_remote_code=True)。
  • 支持多个 LoRA adapter。
  • 调用前通过 set_lora(module_name) 切换 summarizer / extractor / generator adapter。
  • 如果某模块配置为 default，则禁用 adapter，使用原始 ChatGLM。

7.3 LoRA map

lora_map 是 LD-Agent 在 ChatGLM3 路线里做“任务到 LoRA adapter”的路由表。 它不是 memory 内容，也不是 prompt 配置，而是告诉同一个 ChatGLM3 base model：当前这次调用应该启用哪一个 LoRA adapter。 

{
  "EventSummary": args.summary_model,
  "PersonaExtraction": args.persona_model,
  "ResponseGenerator": args.generation_model
}

7.3.1 它解决什么问题

LD-Agent 有三个不同的 LLM 子任务：session event summary、persona extraction、response generation。 官方没有为每个任务单独加载一个完整大模型，而是加载一个 ChatGLM3-6B base model，再给不同任务训练不同 LoRA。 lora_map 就是这三个任务和三个 LoRA checkpoint 路径之间的映射。

换句话说，LoRA 在 LD-Agent 里不是“记忆库”，而是让同一个底座模型在不同任务上表现得像三个专门模型： 一个会总结事件，一个会抽 persona，一个会根据记忆生成回复。lora_map 则是在每次调用前选择 “这次应该像哪个专门模型”。

7.3.2 LoRA 本身在这里是什么

LoRA 是 parameter-efficient fine-tuning 的一种方式。对 LD-Agent 来说，它的工程意义是： 不复制三份 ChatGLM3-6B 完整模型，只在同一个 base model 上挂三个小型 adapter。 base model 提供通用语言能力；adapter 提供特定任务的行为偏置。 

ChatGLM3-6B base model
  + summarizer LoRA  -> EventSummary behavior
  + extractor LoRA   -> PersonaExtraction behavior
  + generator LoRA   -> ResponseGenerator behavior

源码配置里三个 LoRA 都使用相同 PEFT 超参：peft_type=LORA、task_type=CAUSAL_LM、 r=8、lora_alpha=32、lora_dropout=0.1。 差别主要来自训练数据和训练步数。

7.3.3 三个 LoRA 分别训练什么能力

LoRA adapter 训练入口 训练目标 在实验链路里的直接影响
summarizer scripts/summarizer_tuning.sh
Trainer/configs/summarizer.yaml		 把一段 session 对话压缩成简短 event summary。配置中 max_steps=7500。 影响 long-term event memory 的 summary 字段质量；summary 后续会展示给 generator。
extractor scripts/extractor_tuning.sh
Trainer/configs/extractor.yaml		 从一句 user/agent utterance 中抽取 persona trait，或输出 NO_TRAIT。配置中 max_steps=4000。 影响 user traits 和 agent traits 是否准确、是否过度抽取、是否漏抽。

7.3.5 default 的含义

如果某个任务在 lora_map 中对应的值是 "default"，源码会调用 disable_adapter_layers()，即这次任务不使用 LoRA，直接使用原始 ChatGLM3。 README 中也说明 "default" 表示该模块使用 original ChatGLM。 

if self.lora_map[module_name] != "default":
  self.model.enable_adapter_layers()
  self.model.set_adapter(self.lora_map[module_name])
else:
  self.model.disable_adapter_layers()

因此，default 可以理解成一个工程级消融开关：某个模块不加载该任务 LoRA， 只靠 base ChatGLM3 按 prompt 完成任务。它不表示关闭这个模块，也不表示关闭记忆； 它只表示该模块调用时没有使用 task-specific adapter。

7.3.6 载入方式和一个源码细节

初始化 GLMClient 时，源码先收集所有非 default 的 LoRA 路径： self.lora_paths = [path for path in lora_map.values() if path != "default"]。 然后逐个 PeftModel.from_pretrained(..., adapter_name=lora_path) 加载到同一个 base model 上。 后续每次调用只切换 adapter，不重新加载模型。

源码注意点： set_lora(module_name) 直接访问 self.lora_map[module_name]。 所以只要 GLMClient.employ(..., name) 传入的 name 不在 lora_map 里，就会触发 key error。QuickEval.py 的 lora_map 额外加入了 "default": "default"，就是为了可以安全地调用 employ(..., "default")。

7.3.7 对 LD 模块的实际意义

调用名 调用位置 对应 LoRA 任务含义
EventSummary EventMemory.context_summarize() args.summary_model 把上一 session 对话压缩成短事件摘要。
PersonaExtraction Personas.user_traits_update() / agent_traits_update() args.persona_model 从一句话中抽取 user 或 agent 的 trait。
ResponseGenerator Generator.response_build() args.generation_model 基于 context、retrieved memory 和 personas 生成最终回复。

7.3.8 LoRA 在实验里起到什么作用

在 LD-Agent 的 ChatGLM3 实验里，LoRA 起到的是“把一个通用底座模型变成模块化 agent pipeline”的作用。 它不只是提高最终回答质量，也会影响中间记忆状态。因此它在实验中的作用可以分成三层：

层级 LoRA 介入点 实验影响
记忆写入质量 EventSummary LoRA 决定 session 被压缩成什么 long-term event summary。摘要过粗会丢事件连续性； 摘要跑偏会把错误内容写入 memory；摘要太泛会导致后续 generator 即使检索到 memory 也用不上。
Persona 表示质量 PersonaExtraction LoRA 决定 user / agent traits 的准确性。抽得好可以提升个性化；抽得太激进会制造虚假 persona； 抽得太保守则 persona 模块近似失效。
记忆使用能力 ResponseGenerator LoRA 决定最终回复是否真正遵循 LD prompt 中的 <CONTEXT>、<MEMORY>、 <USER_TRAITS>。没有 generator LoRA 时，base ChatGLM3 可能看得到记忆， 但不一定会稳定、自然地使用。

7.3.9 对实验归因的影响

关键实验口径： 在 ChatGLM3 + LoRA 路线中，LD-Agent 的结果不是“纯记忆结构”的效果，也包含三个 task-specific LoRA 的效果。 例如最终回答变好，可能来自更好的 event memory 检索，也可能来自更好的 summarizer、persona extractor 或 generator。

因此分析 LD 实验时要区分四种贡献：

  1. 框架贡献：short-term memory、long-term event memory、persona memory、retrieval 和 prompt 组合。
  2. 记忆内容贡献：event summary 和 persona traits 写得是否准确。
  3. 检索贡献：Chroma 候选、topic overlap、time decay 是否把正确 memory 找出来。
  4. 模型适配贡献：LoRA 是否让 ChatGLM3 更擅长做 summary、trait extraction 和 memory-aware generation。

这也是 LD 官方同时提供 ChatGPT 评测和 ChatGLM3 评测的原因之一：ChatGPT 路线没有 LoRA， 更接近“用强通用模型按 prompt 跑 LD 框架”；ChatGLM3 路线则是“用较小开源模型 + 模块化 LoRA 复现 agent pipeline”。

7.3.10 和 ChatGPT 路线的区别

GPTClient 没有 LoRA，也不会根据 name 切换模型；它只把 name 用于 token 日志统计。因此 lora_map 只属于 ChatGLM3 + LoRA 路线。 这也是为什么 LD-Agent 论文说框架可以使用不同底座模型，但官方工程里 ChatGLM3 路线有明显的 module-specific checkpoint 设计。

7.3.11 对后续复现口径的提示

如果只复现 LD 的 memory 机制，而不使用 ChatGLM3/LoRA，那么应明确说： “复现的是 LD memory-side framework，不复现 LD 的 module-specific LoRA training pipeline。” 因为 LoRA 在官方 ChatGLM3 实验里会影响 memory 写入、persona 抽取和最终回答三处行为。

8. MSC / QuickEval 实验链路

8.1 MSC 数据假设

LD 的实验数据不是一份单一对话文件，而是一组围绕“长期对话记忆”拆分出来的数据： MSC / CC 是最终长对话评测场景，DialogSum 用来训练事件摘要器，persona extraction 数据用来训练人格抽取器， response generation 数据用来训练最终回答模型，Ubuntu IRC 用来做多方对话迁移评测。 因此理解 8.1 的重点不是只看样本数，而是看每类数据在 LD 链路中承担什么职责。

核心结论： MSC / CC 提供“跨 session 的长期历史”和“session 间隔时间”；其他数据集主要服务于 LD 的三个可训练能力： event summary、persona extraction、response generation。也就是说，LD 的记忆系统评测依赖 MSC / CC， 但 LD 的记忆写入、人格抽取和回答生成能力并不完全来自 MSC / CC 原始对话本身。

8.1.1 MSC 和 CC 分别是什么

MSC 是 Multi-Session Chat，来自 Beyond Goldfish Memory: Long-term Open-domain Conversation。 它是人工参与的英文开放域多 session 对话数据集，核心目标是让同一对说话人分多次聊天， 并在后续 session 中自然地回忆、延续和利用之前聊过的内容。对长期记忆实验来说， MSC 的价值在于它不是单轮 QA，也不是单段长文本，而是“同一关系在多次会话中逐渐积累信息”的 benchmark。

在 LD-Agent 里，MSC 是最重要、最可复现的主线数据。官方源码提供了 DataLoader/MSC.py、scripts/msc_glm_eval.sh、 scripts/msc_gpt_eval.sh 和 scripts/msc_glm_sampling.sh。 也就是说，当前开源工程真正能直接跑通的完整长期记忆链路，主要就是 MSC。

CC 是 Conversation Chronicles，来自 Jang, Boo, Kim 2023。 它也是英文多 session 长对话数据集，但构造方式和 MSC 不同：CC 使用 ChatGPT 根据事件图、 人物关系、时间间隔和 session 摘要生成大规模长期对话。它更强调规模、时间跨度和关系类型的多样性。 原始 CC 数据以 episode 组织，每个 episode 通常包含 5 个 sessions，并带有 relationship、time_interval、session-level dialogue 和 summary。

在 LD-Agent 论文里，CC 的角色是作为 MSC 之外的另一个长期对话 benchmark， 用来验证 LD 的记忆方法是否只适配 MSC，还是能迁移到另一种由事件和人物关系驱动的长对话数据。 但要注意，当前 LD-Agent 官方 README 的 TODO 里仍写着 Code and datasets of CC， 所以 CC 在论文实验里出现，但在现有开源 repo 中不是像 MSC 那样完整可直接复现的一等链路。

项目 MSC CC
全称 Multi-Session Chat Conversation Chronicles
数据来源 人工多 session 开放域聊天。 ChatGPT 基于事件图、人物关系和时间间隔生成。
核心目的 测试模型能否在同一对话关系中跨 session 记住过去信息。 测试模型能否在更大规模、更长时间跨度、更明确关系设定中维护长期记忆。
典型结构 一个 conversation 包含 5 个 sessions，每个 session 有多轮双人对话。 一个 episode 包含 5 个 sessions，并带 relationship、time interval、dialogue、summary 等字段。
LD 开源复现状态 源码中有完整 DataLoader 和 evaluation / sampling 脚本。 论文中使用；当前官方 repo README 标注 code 和 datasets 仍待补充。
数据 论文规模 在 LD 实验里的具体用途
MSC / CC 各 4,000 train、500 validation、501 test conversations。 主实验长对话 benchmark。每个 conversation 被组织成 5 个 sessions， 每个 sample 大约 50 个 conversational turns，并带有 session 间隔时间 annotation。 这些时间间隔会进入 time_pass，供 LD 的 time decay 和“多久以前发生”表达使用。
DialogSum 13,460 dialogues；12,460 train、500 validation、1,500 test。 训练 EventSummary 的数据。它把一段对话压缩成事件摘要， 对应 LD 写入 long-term event memory 前的 summary 能力。MSC evaluation 时不直接拿 DialogSum 做检索，而是使用由它训练出的 summarizer LoRA / summarizer 模型。
Persona extraction 由 MSC persona annotations 构建；26,605 train、17,660 validation。 训练 Personas 模块。输入是对话内容，输出是用户或 agent 的 persona trait， 或者判断当前 utterance 没有人格信息。它服务的是“从对话中维护长期 persona 状态”，不是事件记忆本身。
Response generation 结合 MSC/CC 原对话、retrieved memories、personas 和 prompt 构造；34,907 train、11,851 validation。 训练最终 ResponseGenerator。样本不是裸对话，而是把当前 query、short-term context、 retrieved long-term memories、user personas、agent personas 拼成 prompt 后监督生成 gold response。 这一步让模型学会“如何读 LD 的记忆提示词”。
Ubuntu IRC 多方对话迁移评测；311,725 train、5,000 validation、5,000 test。 用于验证 LD 是否能迁移到更复杂的多方对话场景。它不是 MSC 主链路的必要输入， 更像是论文用来说明框架泛化能力的附加评测。

8.1.2 MSC / CC 对话结构

从 DataLoader/MSC.py 看，LD 期望 MSC 数据已经被预处理成“sample -> session -> dialog turns”的结构。 每个 sample 是一个跨时间的长期关系；每个 sample 内有 5 个 session；每个 session 内有多轮 SPEAKER_1 和 SPEAKER_2 的交互。源码消费数据时大致等价于： 

[
  [
    {
      "dialog": [
        {"SPEAKER_1": "user utterance", "SPEAKER_2": "agent response"},
        {"SPEAKER_1": "next user utterance", "SPEAKER_2": "next agent response"}
      ],
      "time_pass": 86400
    },
    {
      "dialog": [...],
      "time_pass": 604800
    }
  ]
]

这里的 SPEAKER_1 在 LD evaluation 中被当作当前用户输入， SPEAKER_2 被当作 gold response。每处理一条 user utterance，系统先检索 memory， 再把 gold response 写回 short-term memory，用来模拟离线 benchmark 中“历史对话真实发生过”的状态。

8.1.3 为什么 session 间隔时间重要

MSC / CC 的关键不是只有 5 个 sessions，而是这 5 个 sessions 之间有时间间隔标注。 LD 会把 time_pass 累加到 memory_bank.current_time_pass： 

current_time = time.time() + memory_bank.current_time_pass
memory_bank.current_time_pass += dataset[sample_id][session_id]["time_pass"]

这使得同一段历史在不同 session 中会呈现出不同的“过去时间”。它会影响两件事：

  1. context boundary： context_retrieve() 判断当前 utterance 和 short-term memory 中上一条 utterance 的时间距离。 如果距离超过 dist_thres，LD 认为进入了新的时间段，会把旧 short-term 对话汇总并写入 long-term memory。
  2. time decay： relevance_retrieve() 在计算相关 memory 时，不只看语义相似度， 还会根据 memory 距离当前时间有多远进行衰减，并生成类似“x days ago”的过去时间描述。

所以 MSC / CC 的时间 annotation 是 LD 区分“短期上下文”和“长期记忆”的实验基础。 如果没有这个字段，LD 仍然可以做向量检索，但它的原论文设定中的 time decay 和跨 session 老化机制就不完整。

8.1.4 官方 MSC evaluation 的真实执行方式

官方脚本使用 dataset/MSC/sequential_test.json，并设置 test_num=501。 DataLoader/MSC.py 的默认设置是 min_session=1、max_session=5， 因而实际流程是：

  1. session 1 初始化： memory_bank_init() 遍历 dataset[sample_id][0]["dialog"]。 这一段只建立历史，不生成最终评测 response。
  2. 累加 session 1 后的时间： 初始化完成后，代码执行 current_time_pass += dataset[sample_id][0]["time_pass"]， 让后续 session 发生在“未来某个时间点”。
  3. 评测 session 2-5： 代码依次处理 session index 1、2、3、4。每条 user utterance 都会先检索 short-term context 和 long-term relevant memories， 再构造 prompt 生成 response，最后和 gold SPEAKER_2 比 BLEU、ROUGE、Distinct。
  4. 每个 session 后继续推进时间： 评测完一个 session 后继续累加该 session 的 time_pass， 保证下一 session 的检索可以看到更久远的历史。

这意味着论文里的“5 sessions”不是简单拼成长文本输入模型，而是被 LD 用作一个带时间推进的记忆仿真环境： 第一 session 负责冷启动记忆，后四个 sessions 负责检验记忆能否被写入、摘要、检索并参与生成。

8.1.5 五类数据分别训练或评测哪个模块

数据源 对应模块 它提供的监督信号 和 MSC evaluation 的关系
DialogSum EventSummary 把多轮 dialogue 压缩为事件 summary。 训练 summary 能力；evaluation 时用于生成 long-term event memory 的文字内容。
Persona extraction Personas 从 utterance 中抽取 persona trait，或输出无 trait。 训练长期 persona 更新能力；evaluation 时用历史对话持续维护用户和 agent traits。
MSC / CC response generation ResponseGenerator 在给定 query、context、retrieved memories、personas 的情况下生成 gold response。 训练模型理解 LD prompt 中的多块记忆信息，而不是只学习普通聊天。
MSC / CC sequential test EventMemory + Personas + ResponseGenerator 长对话离线评测。 最终验证完整 LD pipeline：summary、storage、retrieval、persona update、response generation。
Ubuntu IRC 完整或迁移后的 LD pipeline 多方对话场景中的生成质量。 补充评测；用于说明 LD 不只适用于双人 MSC/CC。

8.1.6 复现时需要注意的边界

  • 论文规模和开源脚本不是同一件事： 论文附录给出 MSC、CC、DialogSum、persona extraction、response generation、Ubuntu IRC 的规模； 但源码仓库主要提供 MSC 和 QuickEval 链路，实际数据需要按 README 从外部下载并放入 dataset/。
  • CC 在当前开源 repo 中不是完整一等实现： README 的 TODO 明确提到 CC 的 code 和 datasets 仍待补充。因此复现时更可靠的主线是 MSC， CC 更适合作为论文描述中的对照数据，而不是当前 repo 可直接跑通的完整链路。
  • 数据规模表不能直接等价于一次 evaluation 的样本量： 例如官方 MSC evaluation 脚本通常跑 sequential_test.json 的 501 test conversations； summarizer、extractor、generator 的训练样本数则属于不同训练任务。
  • LD 的主实验评测是离线 teacher-forcing 风格： 历史 response 使用数据集里的 gold SPEAKER_2 写入 memory， 这样做是为了让所有方法面对同一段真实历史，而不是让模型自己的早期错误污染后续记忆。

8.2 memory_bank_init()：第一 session 初始化

源码会遍历 dataset[sample_id][0]["dialog"]，即第一 session。 对每条 user utterance：

  1. 调用 context_retrieve，把 user query 写入 short-term memory。
  2. 调用 relevance_retrieve，虽然第一 session 初始通常还没有长期记忆。
  3. 把数据集里的 gold SPEAKER_2 response 写入 short-term memory。

该阶段不生成待评估 response，主要用于建立历史上下文。

8.3 interative_eval()：后续 session 评测

对 session 2-5 的每条 user utterance：

current_time = time.time() + memory_bank.current_time_pass
context_memories = context_retrieve(current user)
related_memories = relevance_retrieve(current user)
merged_context = current short-term context
merged_relevant_memory = retrieved summaries or "No relevant Memories."
append gold SPEAKER_2 to short_term_memory
current_user_traits, current_agent_traits = personas.traits_update(gold pair)
response = generator.response_build(...)
score = BLEU / ROUGE / Distinct against gold SPEAKER_2
实验解释： LD 的自动评测为了模拟“真实历史交互”，在生成当前 utterance 前把所有 preceding ground-truth conversations 输入框架，自动抽 personas 和 memories。它评的是：在真实历史已知的离线 benchmark 中，LD 框架是否帮助生成更接近 gold response 的回答。

8.4 QuickEval

DataLoader/QuickEval.py 不运行 EventMemory / Personas。它读取已经采样好的 prompt 数据： system prompt、user prompt、reference response，然后只调用 ResponseGenerator 评估生成质量。

12. 论文描述与源码实现差异

这一节很重要，因为后续写“复现 LD”时不能只按论文公式，也不能只按源码行为，需要明确口径。

点位 论文描述 源码实际 理解
Retrieval score semantic relevance + topic overlap，再乘 time decay。 默认路径主要用 topic overlap * time decay；semantic distance 阈值只在 ori_mem_query 分支明显起作用。 官方源码默认更偏 topic-based retrieval。
Session interval threshold 附录写 β=600 seconds。 context_retrieve() 中是 one_hour_seconds = 60 * 60。 论文参数和源码阈值不一致。
Chroma document 论文讲 memory bank 保存 event summary representation。 session 写入时 document/key 是 topics 字符串，summary 在 metadata。 源码把 topic key 放在 Chroma document 中，summary 主要用于 prompt 展示。
Persona 默认窗口 persona 动态维护。 默认 max personas 为 0，但切片逻辑会保留全部。 不是禁用 persona，而是几乎不过滤。
自动评测交互方式 模拟真实历史交互。 用 preceding ground-truth conversations 更新 memory/persona。 离线 benchmark，历史不由模型自生成。
Model-agnostic 框架可部署到不同模型。 源码支持 ChatGPT 和 ChatGLM3；训练器主要服务 ChatGLM3 LoRA。 概念上可替换，工程上对 ChatGLM3 有较强实现绑定。

13. 后续可细化问题清单

后续如果要继续细拆，可以按下面问题逐项展开。

13.1 Event Memory 可追问

  • LD 原版 ChromaDB collection 里 document、metadata、ids 分别是什么？
  • relevance_retrieve 在 ori_mem_query=False 和 True 下分别如何选 memory？
  • 为什么论文写 semantic score，但源码默认分支几乎不显式使用 semantic score？
  • topic overlap 是否只选一个 best memory？是否支持 top-k？
  • session boundary 用 600 秒还是 3600 秒，论文与源码如何解释？
  • summary 是存 Chroma document 还是 metadata？这个对复现有何影响？

13.2 Persona 可追问

  • 当前 user utterance 抽出的 persona 是否参与当前轮生成？
  • agent persona 的更新为什么在 merged agent traits 之后？
  • NO_TRAIT 的判断会不会误伤有效 trait？
  • 默认 max_user_personas=0 是否是源码 bug 还是有意设计？

13.3 Generator 可追问

  • LD prompt 中 context、memory、user traits、agent traits 的优先级如何体现？
  • 为什么输出限制为 30 words？这是否影响长期记忆展示？
  • sampling 生成的数据和 generator tuning 数据如何关联？

13.4 实验链路可追问

  • MSC 实验到底哪些地方使用 gold response？
  • LD 的 automatic evaluation 是否能证明“关系连续性”？
  • human evaluation 的 memory retrieval task 如何设计？
  • module ablation 中 event memory、user persona、agent persona 的贡献如何解释？

13.5 后续与我们方法对照入口

  • M0 是否要采用 LD strict mode：relevance_memory_number=1、context_memory_number=30？
  • 中文 topic extraction 应如何替代 spaCy noun lemma，才算合理复现？
  • 我们是否应该让 Chroma document 改为 topic key，而 summary 只进 metadata？
  • 我们是否应该把当前 user trait 加入本轮 M0 payload？
  • M1/M2/M3 的 relational overlay 与 LD 的 event/persona memory 是互补还是替代？
