计划实验与当前工程实现对比

版本：2026-06-08 · 项目：LongMemoryTest · 范围：只展开两条路线和 1-5 节，不预设最终结论

阅读方式： 这份文档先不判断哪条路线一定更好，只把“计划实验路线”和“当前工程路线”分别讲清楚。 重点是确认两者的实验对象、变量、输出结果和论文可解释性到底有什么区别。 后续是否采用、如何改 method 口径、是否做附录 sensitivity analysis，等待下一步讨论。

1. 先把两条路线说清楚

现在容易混在一起的点是：两条路线都叫 M0，也都参考 LD-Agent 的普通长期记忆思想； 但它们对“记忆”这个实验对象的定义不同。计划实验路线把记忆视为一份受控的结构化上下文； 当前工程路线把记忆视为一个会写入、压缩、检索并输出 payload 的 runtime。

路线 A：计划实验路线

计划实验路线的 M0 是 LD-Agent-style generic memory payload。 它复用 LD-Agent 的内容类型，但不复用 LD-Agent 的检索、存储、topic rerank 或运行时状态机。

在这条路线里，每个 probe 到来时，实验脚本直接给模型一份条件允许的记忆： generic profile、user traits、agent traits、session summaries、ordinary event memories 和 recent context。

pre-built payload direct structured injection 主变量是记忆内容粒度

路线 B：当前工程路线

当前工程路线的 M0 是 LD-Agent-compatible memory-only runtime。 它不使用 LD-Agent 的 Generator、ChatGLM3、LoRA 或 benchmark 评测链路，但保留记忆侧的运行行为。

在这条路线里，每个 turn 前，M0 runtime 先根据当前 user message 检索已有普通记忆； 每个 turn 后，只把 M0 条件的用户输入和 M0 回答写回普通记忆。M1/M2/M3 读取同一份 M0 search output，再追加关系记忆层。

runtime memory write / summarize / retrieve M0 search output shared by overlays

1.1 两条路线的最小流程

步骤 计划实验路线 当前工程路线
记忆来源 实验前由 trajectory、daily messages、event themes、probe annotations 或构造规则生成。 运行中由 LDAgentMemoryRuntime 从已完成 M0 turns 写入；也可从 snapshot 恢复。
probe 前发生什么 直接选择该 probe 对应的 condition-specific memory payload。 retrieve_payload(message) 被调用；可能触发 day boundary flush，再检索 event/persona memory。
模型看到什么 预构造的结构化自然语言记忆。 M0 short-term session、retrieved long-term event memories、persona traits、retrieval metadata；M1/M2/M3 额外看到 relational overlay。
回答后发生什么 通常不改变 memory payload；下一个 probe 仍读预构造记忆。 四条件回答结束后，M0 runtime 记录 M0 turn，更新 short-term/persona；跨 day 时写 session summary。
主要控制变量 不同 memory representation 的内容差异。 同一 M0 runtime 的普通记忆检索输出，加上不同 relational overlay 粒度。

1.2 两条路线中“M0”的含义不同

问题 计划实验路线中的 M0 当前工程路线中的 M0
M0 是什么？ 一个强普通长期记忆条件，代表 persona + session summary + ordinary event memories。 一个普通长期记忆 runtime，代表 LD-Agent memory-side 的可运行基线。
M0 强在哪里？ 它能直接读到被构造好的普通长期记忆内容，不缺失、不检索错。 它具备写入、摘要、persona、检索和恢复能力，更像一个真实长期记忆 agent 的普通记忆底座。
M0 弱在哪里？ 不是一个完整 runtime，不能测试 memory write/retrieve 的实际行为。 会受到 summary 质量、topic tokenization、retrieval miss、time decay 等因素影响。
M0 不该看到什么？ 不能看到 recurring event-line summaries、shared strategies、relational anchors、probe/gold/judge 信息。 同样不能看到关系记忆、BEI、gold strategy、probe type、failure mode、M2/M3 anchors；代码和测试对此有保护。

1.3 两条路线回答的是不同层级的问题

研究问题层级 计划实验路线更直接回答 当前工程路线更直接回答
表征问题 当记忆内容都准确给到模型时，不同记忆粒度是否改变 relational expectation 表现？ 在普通 runtime 检索输出相同的前提下，relational overlay 是否带来增量收益？
系统问题 不是主问题。计划实验故意弱化 retrieval/writeback 变量。 M0 是否能作为可审计、可恢复、可运行的普通长期记忆基线？
审稿质疑 可能被问：这是不是 oracle memory injection，而不是 agent memory baseline？ 可能被问：结果是否混入 retrieval quality，而不只是 memory representation？
错误分析重点 underuse、overuse、wrong use、boundary overstep、alienation response。 除左侧外，还要看 retrieval miss、wrong event hit、summary too generic、persona noise。

2. 计划实验会产出什么结果形态

本节统一使用“计划实验”这个名称。计划实验的核心是先构造好所有条件的记忆包， 再在同一个 prompt 外壳、同一个 responder model、同一个当前 user turn 下比较输出。

2.1 计划实验的目标

计划实验不是为了证明某个工程检索系统更好，而是为了把“普通长期记忆”和“关系型长期记忆”拆开。 更具体地说，它要让同一个模型在同一个当前用户输入下，只因为可读记忆层级不同而产生不同回答， 从而观察 relational expectation 是否真的需要更高粒度的关系记忆。

目标 对应比较 要观察的现象 需要避免的混淆
建立下界 Current-only vs 其他条件 没有长期记忆时，模型是否把用户当成陌生人，是否要求用户重讲背景，是否只能给泛化建议。 Current-only 仍应保留同一轮必要短上下文，不能故意削弱到不自然。
建立普通长期记忆基线 M0-plan vs Current-only 普通 persona、session summary、ordinary event memory 是否已经能改善个性化、连续性和具体性。 M0 不能看到关系型事件线、共同策略、BEI、gold strategy 或 probe 信息。
测试结论级关系记忆 M1-plan vs M0-plan 只加入稳定偏好、回应风格、关系期待、边界约束后，回复是否更像熟悉的长期陪伴对象。 M1 不能借用具体事件过程、日期、原话或细节锚点。
测试事件摘要级关系记忆 M2-plan vs M1-plan / M0-plan 加入跨天事件线、状态变化、prior handling strategy 后，是否更能接住“这条线又来了”“不用从头解释”。 M2 仍不能读取原始全文、具体场景细节、共同语言和未筛选细节。
测试细节锚点关系记忆 M3-plan vs M2-plan 加入必要细节、具体场景、共同语言和调用边界后，是否提升自然细节使用和熟悉感。 M3 要观察过度调用、机械背日志、越界熟悉和细节错配风险。

2.2 计划 M1/M2/M3 的核心区别

计划里的 M1/M2/M3 应该是粒度递增，而不是简单把内容越塞越多。 三层的关键差异不是“记得多不多”，而是“记忆表示是否从稳定关系结论，进入事件轨迹，再进入可控细节锚点”。

层级 一句话定义 保存什么 明确不保存什么 主要测试点
M1-plan
Conclusion-level		 保存关系层面的稳定结论，不保存具体事件过程。 稳定偏好、回应风格、关系期待、关键判断、边界约束、不要做什么。 例如：用户偏好直接自然、少废话；焦虑时需要先拆事实和行动边界；不喜欢客服式寒暄。 具体日期、跨天事件过程、原话、具体场景、细节锚点、BEI 标注、gold response strategy。 看抽象关系画像是否足以改善语气、边界、熟悉感和“不要陌生化”的基本能力。
M2-plan
Event-summary		 在 M1 基础上保存关系相关的事件轨迹和状态变化。 跨天主题出现记录、事件线摘要、状态变化、阶段进展、处理结果摘要、prior handling strategy。 例如：幼儿园不稳定在 D1/D4/D10 持续出现；消息仍模糊；用户还没有正式通知。 原始全文、原话、完整历史片段、具体门口画面、共同短语、未筛选细节、细节级调用边界。 看模型能否接住“这是同一条线的延续”，并基于事件进展回应，而不是只重复稳定偏好。
M3-plan
Detail-anchor		 在 M2 基础上保存服务当前判断的必要细节和使用边界。 具体场景、必要细节、共同语言、关系锚点、响应边界、误用边界、当前任务相关细节。 例如：用户真正担心的是孩子被现实变动反复折腾，而不只是换不换幼儿园；回应应接住孩子稳定感。 未存事实、无关隐私细节、完整原始历史、为了显得熟悉而机械背诵的日志、和当前任务无关的细节。 看细节锚点是否提升 context specificity 和 natural detail use，同时观察 overuse、misrouting 和 boundary risk。

2.3 M1/M2/M3 在同一条输入下的具体差别

下面用“孩子幼儿园可能不稳定”这条线做例子。假设当前用户说： 这条线我不想从头解释了。 三层关系记忆给模型的不是同一种信息。

层级 可用记忆示例 理想回应倾向 容易出现的失败
M1-plan 用户偏好直接、自然、少废话；焦虑或反复卡住时，先拆事实、风险、行动边界和下一步； 用户期待熟悉但不过度亲密的长期陪伴对象。 先承认“不用从头讲”，用直接语气回应；给出简短下一步框架；避免客服式寒暄或空泛安慰。 只能知道用户喜欢什么回应方式，但不知道“这条线”具体是哪条、之前发展到哪一步。
M2-plan “孩子幼儿园可能不稳定”曾在 D1、D4、D10 出现，是跨天持续主题； 幼儿园不稳定的消息仍然模糊，用户还没有拿到正式通知或具体原因。 能接上这是幼儿园不稳定这条持续线；先帮用户确认当前仍处在“信息模糊、未正式通知”的阶段； 把下一步限定在确认信息来源、正式通知和可行动窗口。 可能只复述“之前提过幼儿园”，但没有接住用户真正的情绪点；也可能把事件线和其他主题混起来。
M3-plan 用户真正担心的是孩子被现实变动反复折腾，而不只是换不换幼儿园； 调用边界：回应应接住孩子稳定感，而不是只给换园清单。 自然说出“不只是换不换园，你更担心孩子又被现实变动折腾”这一层； 再把行动拆成确认通知、保护孩子稳定感、给自己留决策窗口。 可能机械背“孩子稳定感”这个锚点；或者在用户当前只想确认事实时，过度展开情绪解释。

2.4 M1/M2/M3 和 probe 类型的关系

probe 类型 M1 主要能提供 M2 额外提供 M3 额外提供
P1 Current Understanding 根据稳定偏好，用合适语气理解当前请求。 把当前请求放回持续事件阶段。 用具体锚点识别当前话语背后的真实担心。
P2 Memory Invocation 知道应该避免陌生化，但缺少具体事件线。 知道该调用哪条跨天主题线。 知道调用哪个细节才自然，以及哪些细节不该硬提。
P3 State Transformation 知道用户焦虑时偏好事实优先。 知道用户状态如何从前几天推进到现在。 能抓住触发状态变化的具体场景或细节。
P4 Boundary 提供熟悉但不过度亲密的总体边界。 提供事件处理边界，例如当前信息还不够，不能替用户下结论。 提供细节调用边界，例如细节只能服务当前判断，不能机械背日志。
P5 Alienation Avoidance 知道不能像陌生客服一样让用户重讲。 能接住“这条线”具体指哪条持续事件。 能用一个自然细节让用户感到被记得，但不过度表演熟悉。
P6 Natural Detail Use 一般不负责细节；主要负责风格。 负责摘要级具体性。 负责必要细节和共同语境的自然调用。

2.5 计划实验的数据流

Controlled trajectory
  ├─ persona / life domains
  ├─ recurring event lines
  ├─ daily interactions
  ├─ targeted probes
  └─ BEI / required memory / failure mode annotations
        ↓
Pre-built condition memory payloads
  ├─ Current-only
  ├─ M0-plan: generic profile + session summaries + ordinary event memories
  ├─ M1-plan: conclusion-level relational memory
  ├─ M2-plan: M1 + relational event summaries
  ├─ M3-plan: M2 + detail anchors
  └─ Oracle / relevant history
        ↓
Same responder model + same prompt shell
        ↓
Responses + D1-D4 scores + P1-P6 breakdown + error analysis

2.6 计划实验中的 memory payload 形态

条件 模型可读内容 实验想观察的差异
Current-only 当前 user turn + 固定短上下文。 没有长期记忆时，模型是否泛化、陌生化、要求用户重讲背景。
M0-plan user profile、user traits、agent traits、ordinary session summaries、ordinary event memories、recent context。 普通长期记忆是否已经足以支撑 relational expectation。
M1-plan M0 不一定作为 base；主要增加稳定偏好、回应规范、关系期待、边界约束。 抽象结论是否能改善语气、边界和稳定响应规范。
M2-plan M1 + 跨天事件线、状态变化、prior handling strategy、shared event trajectory。 事件轨迹是否改善 continuity-sensitive 和 context-specific responses。
M3-plan M2 + 具体场景、共同语言、细节锚点、边界敏感 cues。 细节锚点是否提高 specificity，同时是否引入 overuse 或 boundary risk。

2.7 计划实验会得到的主要表格

结果表 内容 解释方式
主效果表 Current-only、M0-plan、M1-plan、M2-plan、M3-plan、Oracle 的总体分数。 看普通长期记忆与关系记忆的整体差距。
D1-D4 维度表 Situated Intent、Emotional Attunement、Contextual Specificity、Continuity-Sensitive Response。 看哪个 memory level 对哪类 ToM/关系期待能力更敏感。
P1-P6 probe 类型表 current understanding、memory invocation、state transformation、boundary、alienation avoidance、natural detail use。 看不同 probe 类型上 M0/M1/M2/M3 的差异模式。
错误类型表 underuse、overuse、wrong memory、shallow recall、boundary overstep、alienation response。 因为没有 runtime retrieval，错误更多归因于模型是否正确使用给定 memory。
案例分析表 每类 probe 的代表性成功/失败样本。 展示关系记忆和普通记忆在具体回复风格上的差别。

2.8 计划实验的优点和边界

优点 边界
变量干净，memory representation 的差异最清楚。 不能直接说明真实 runtime 是否能写入和检索出这些 memory。
便于人工检查 memory payload 是否泄漏 BEI、gold strategy 或关系锚点。 如果 memory 是按 probe 预构造，容易被质疑接近 oracle relevant memory。
运行成本低，不需要维护长期状态、snapshot 或恢复逻辑。 无法区分 retrieval failure、summary failure 和 response failure。

3. 当前工程实际结果形态

当前工程的 M0 是运行时对象，不是静态 payload。核心类是 src/long_memory_test/memory/ld_agent_runtime.py 里的 LDAgentMemoryRuntime。 它在注释里明确写了：保留 short-term session memory、session-level event summarization、 topic-overlap/time-decay retrieval 和 Personas-style trait extraction；不要求 Chroma/spaCy。

3.1 当前工程的 turn-level 流程

For each user turn:

1. Build the shared current input
   - message_id / day / topic / user_message / domains / turn_type

2. Retrieve M0 payload before generation
   - m0_memory_runtime.retrieve_payload(message)
   - prepare_for_turn(message)
   - if day boundary: flush previous short_term_session into event memory
   - retrieve event memories with topic overlap + time decay
   - collect current persona traits
   - render M0 memory_context

3. Build condition payloads
   - M0: runtime M0 payload
   - M1: M0 base payload + conclusion-level relational overlay
   - M2: M0 base payload + M1 + event-summary relational overlay
   - M3: M0 base payload + M1 + M2 + detail-anchor overlay

4. Generate responses
   - same responder model
   - same current user_message
   - condition-specific memory_context
   - optional condition-level parallel workers

5. Write back only M0
   - record_completed_turn(message, M0 answer)
   - append user turn to short_term_session
   - update user/agent persona traits
   - save checkpoint / snapshot

3.2 M0 runtime 内部状态

状态字段 当前工程含义 实验审计价值
current_session_day 当前 short-term session 属于哪一天；day 改变时触发 session flush。 能确认跨天记忆何时被压缩为 long-term event memory。
short_term_session 当前 session 内已完成的 M0 user turns 和对应 M0 answer。 能确认模型当前短上下文来自哪些真实已完成 turn。
memories 普通 event memory 和 persona memory 的统一存储，默认在 JSON snapshot 中恢复。 能检查 M0 是否泄漏关系记忆，或是否只保存 ordinary memory。
user_traits / agent_traits Persona-style 抽取得到的 traits 列表。 能检查 persona 是否过度泛化、噪音过多或污染回答。
actions 记录 short-term append、event memory add、persona add/update 等记忆动作。 能重建每条 memory 的来源和写入时机。
memory_llm_failures 记录 summary/persona/Chroma retrieve 等失败与 fallback。 能避免把 LLM writer 失败误判成 memory representation 失败。

3.3 M0 event memory 写入形态

当 day/session boundary 出现时，当前工程会把上一 session 的 short-term turns 拼成 (line n) User: ... 形式，然后生成一条 ordinary session summary。 这条 memory 的 metadata 模仿 LD-Agent event memory 的字段。 

{
  "memory_type": "event_memory",
  "summary": "ordinary session-level summary",
  "raw_dialogue": "User/Agent turns from the flushed session",
  "source_session": "D01",
  "source_turn_ids": ["D01_M001", "D01_M001_F001"],
  "ld_agent_metadata": {
    "idx": 0,
    "dialog": "",
    "time": 100000.0,
    "topics": "幼儿园,稳定,孩子,...",
    "datatype": "text",
    "summary": "ordinary session-level summary"
  }
}

3.4 M0 persona memory 写入形态

每个 M0 turn 完成后，runtime 会从 user inquiry 和 M0 response 中抽取 traits。 user trait 和 agent trait 都写入普通 persona memory；这模拟 LD-Agent Personas 模块， 但不使用 LD 原版 LoRA extractor。 

{
  "memory_type": "persona_memory",
  "summary": "User prefers concrete planning over generic reassurance.",
  "source_session": "D01",
  "source_turn_ids": ["D01_M001"],
  "ld_agent_metadata": {
    "speaker": "user",
    "datatype": "text",
    "summary": "User prefers concrete planning over generic reassurance.",
    "source": "LD-Agent Personas.traits_update"
  }
}

3.5 M0 retrieval 输出形态

当前工程不是把所有 ordinary event memories 全部注入。它会根据当前 message 构造 query， 对 event memory 做 topic-overlap + time-decay scoring，返回 top-k hits。 

{
  "retrieval": {
    "strategy": "ld_agent_relevance_overlap_time_decay",
    "top_k": 5,
    "query": "孩子幼儿园可能不稳定 ...",
    "event_memory_count": 1,
    "persona_memory_count": 3,
    "event_hits": [
      {
        "score": 0.5123,
        "overlap_score": 0.62,
        "overlap_count": 4,
        "time_decay": 0.826,
        "memory": {
          "memory_id": "event_memory_xxx",
          "summary": "User discussed possible kindergarten instability and wanted practical planning.",
          "source_session": "D01"
        }
      }
    ],
    "persona_hits": [...]
  }
}

3.6 M0 memory_context 输出形态

最终给 responder 的 M0 memory_context 是自然语言，但里面包含 retrieval 结果和审计线索： 

LD-Agent memory baseline (memory-only).
Reference: leolee99/LD-Agent Module/EventMemory.py and Module/Personas.py;
response generator/checkpoints are not used.
Implementation: LD-compatible JSON backend; reproduces short-term session memory,
session summary, persona traits, topic-overlap retrieval, and time decay.

Short-term memory bank:
- [TURN ...] User: ...

Retrieved long-term event memories:
- User discussed possible kindergarten instability ...
  (source_session=D01, topics=..., overlap=..., time_decay=...)

Persona traits:

3.9 当前工程的污染控制和 answer 回流

当前工程已经采用隔离模式。M1/M2/M3 的回答会被保存到本轮日志的 variants 中， 用于后续评估和对比；但它们不会写回 M0 runtime，也不会写回 M1/M2/M3 关系记忆文件。 也就是说，M1/M2/M3 的 answer 是实验输出，不是后续记忆输入。 

同一 user turn
  ↓

  ↓
variants["M0"].assistant_answer  → 写回 M0 runtime
variants["M1"].assistant_answer  → 只保存日志，不写回记忆
variants["M2"].assistant_answer  → 只保存日志，不写回记忆
variants["M3"].assistant_answer  → 只保存日志，不写回记忆

M1/M2/M3 关系记忆 writeback 当前没有运行时写回；关系记忆来自预构造 memory_conditions payload。 保证同一轮比较中关系层是固定输入，而不是被模型输出动态改写。
短期上下文回流 SHORT_TERM_CONTEXT_MODE = shared_user_turns_only，后续短期上下文只追加同一个 user turn，不追加任何 assistant answer。 避免 M0/M1/M2/M3 各自回答进入后续上下文，造成条件分叉和不可比较。

M1 不读事件线，不读 details，不根据当前 message 动态筛选事件。它只拼接静态常量 REL_CONCLUSION_MEMORY，并给固定的 source ids： m1_response_style_direct 和 m1_anxiety_fact_first。

  "结论级关系记忆：" + REL_CONCLUSION_MEMORY

REL_CONCLUSION_MEMORY =
  用户偏好直接、自然、少废话；
  不喜欢客服式寒暄和空泛安慰；

  熟悉但不过度亲密，必要时明确区分已知和推测。

3.10.5 M2：_build_m2_summary() 的完整逻辑

M2 的目标是摘要级事件/状态记忆。它不是把原始 history 塞进去，而是把“同主题是否跨天出现” 和“相关事件的 M2 anchor 或事件状态摘要”转成自然语言。 

_build_m2_summary(topic, topic_history, related_events):
  lines = []

  if topic_history:
      days = ", ".join("D{day}" for each item in topic_history)
      lines.append("- 「{topic}」曾在 {days} 出现，是跨天持续主题。")

  for event in related_events[:6]:
      anchors = [
          anchor
          for anchor in event["memory_detail_anchors"]
          if anchor["min_memory_level"] == "M2"
      ]

      if anchors:
          for anchor in anchors:
              lines.append("- " + anchor["text"])
      else:
          lines.append("- D{event.day} {event.title}，状态：{event.status}。")

  if lines:
      return unique(lines), preserving order
  else:
      return "- 当前只有普通主题摘要，没有可追溯事件线。"
M2 规则点 具体含义
同主题历史只来自 daily messages _topic_history() 只扫描 daily_messages["messages"]，并限制 day <= 当前 day。probe 自身不会被当成 daily history。
相关事件来自 message refs _related_events() 只读取当前 message 上显式挂的 event_refs、primary_event_id、related_event_id，不会全文搜索 timeline。
最多处理前 6 个 related events for event in related_events[:6] 控制 M2 摘要长度，避免一次塞入过多事件。
优先使用 M2 anchors 如果 event 有 min_memory_level == "M2" 的 anchors，就只把这些 anchor 的 text 加入摘要。
没有 M2 anchor 时回退到事件标题/状态 回退句是 D{day} {title}，状态：{status}。，仍然是摘要级，不引入细节锚点。
去重但保持顺序 _unique_strings() 保证重复 anchor 不重复出现，但不改变原始顺序。
M2 source_detail_ids _source_detail_ids(related_events, max_level="M2") 只收集 M2 anchors 的 detail_id。

3.10.6 M3：_build_m3_details() 的完整逻辑

M3 的目标是细节级关系锚点。它在 M2 已经给出的摘要级事件线之上，选择可以服务当前判断的细节。 这里的关键不是“把所有细节都给模型”，而是通过 min_memory_level 和 target_detail_ids 控制哪些细节进入 M3。 

_build_m3_details(message, related_events):
  target_detail_ids = set(message.get("target_detail_ids", []))
  lines = []

  for event in related_events:
      for anchor in event["memory_detail_anchors"]:
          detail_id = anchor["detail_id"]
          min_level = anchor["min_memory_level"]

          if min_level == "M3" or detail_id in target_detail_ids:
              lines.append("- " + anchor["text"])

              if anchor["expected_response_mode"]:
                  lines.append("  调用边界：" + anchor["expected_response_mode"])

  lines.append("- 使用边界：细节只能服务当前判断，不能机械背日志，不能补未存事实。")
  return unique(lines), preserving order
M3 规则点 具体含义
M3 继承 M2 m3_context = m2_context + "\n细节级关系锚点：\n" + _build_m3_details(...)，所以 M3 payload 包含 M1 结论、M2 摘要和 M3 细节。
遍历所有 related events M3 没有 [:6] 截断；它遍历当前 message 显式关联到的所有 events。
默认纳入 M3 anchors 只要 anchor 的 min_memory_level == "M3"，就进入 M3 细节锚点。
target_detail_ids 可以强制纳入当前 probe 目标细节 如果当前 message 的 target_detail_ids 指向某个 detail，即便它不是 M3 level，也会被纳入 M3 details。这用于 targeted probe 对齐要测试的细节。
expected_response_mode 变成调用边界 如果 anchor 有 expected_response_mode，M3 不只给事实，还给“应该怎么用这个细节”的边界说明。
固定追加全局使用边界 每个 M3 details 最后都会追加：细节只能服务当前判断，不能机械背日志，不能补未存事实。
M3 source_detail_ids _source_detail_ids(related_events, max_level="M3") 收集 M2 和 M3 anchors 的 detail_id，因为 M3 payload 同时包含 M2 摘要和 M3 细节。

主失败类型 response model 不会用已给记忆，或用得过度/错误。 除了 response failure，还有 write failure、summary failure、retrieval failure、persona noise。 当前工程错误分析更复杂。 结果表最好增加 retrieval-stage diagnostics。
最强质疑 是不是 oracle memory injection？ 是不是把 retrieval 质量混入 representation 结论？ 两条路线需要不同的防御策略。 计划实验需要 sensitivity；当前工程需要 retrieval diagnostics。

5. 当前工程和 LD-Agent 原版的关系

当前工程不是完整复现 LD-Agent，也不是只借一句“persona + event summary”的概念。 更准确地说，它是一个 memory-side compatible reproduction： 复现 LD-Agent 中和普通长期记忆有关的运行结构，同时替换或去掉不适合本实验的工程依赖、模型训练和 benchmark 链路。

Module/Personas.py 从 user/agent utterances 抽取 persona traits，并在 response prompt 前提供 traits。 部分进入 保留 Personas-style trait extraction 和 user/agent traits memory；不用 LD 原版 LoRA extractor。
Module/Generator.py 把 context、memory、user traits、agent traits 拼成 LD prompt 并生成 response。 不进入 当前实验统一使用本项目 responder prompt，避免 generator 差异成为变量。
Module/Clients.py 支持 ChatGPT API、ChatGLM3、LoRA adapter 切换。 不进入 当前工程使用本项目 LLM client；只保留 memory writer 调用逻辑。
Trainer/lora_tune.py 训练 EventSummary、PersonaExtraction、ResponseGenerator 三个 LoRA。 不进入 不使用 LD checkpoint 或 LoRA，避免训练效果混入记忆变量。
DataLoader/MSC.py 用 MSC sequential test 跑长期对话离线评测；历史 response 使用 gold SPEAKER_2。 不进入 当前实验使用 ReMem-RE controlled trajectories 和 targeted probes。
nlgeval BLEU、ROUGE、Distinct 等开放域生成指标。 不进入 当前实验使用 ToM / relational expectation 维度，不以 lexical overlap 为主。

5.2 EventMemory 对照

机制 LD-Agent 原版 当前工程 差异说明
short-term memory 当前 session 的原始 turns，源码中是 list；MSC 里 user query 和 gold response 都写入。 short_term_session 保存当前 session 的 M0 user turn 和 M0 answer。 当前工程不用数据集 gold response 写历史，而是用 M0 条件回答写回，避免其他条件污染。
session boundary 根据时间间隔判断是否跨 session；超过阈值则 flush。 根据 day/session boundary flush；prepare_for_turn 在新 day 到来时写 event memory。 本实验已有 30 天 structured timeline，day boundary 比真实秒级间隔更可控。
session summary 把上一 session turns 拼成 conversation，生成 20 words 以内事件摘要。 同样拼接 line 格式，使用当前实验 LLM 或 deterministic fallback 生成 ordinary summary。 保留 summary 思想，但不使用 LD summarizer LoRA。
memory metadata idx、dialog、time、topics、datatype、summary。 保留同类 metadata，并写入 ld_agent_metadata。 用于审计兼容性和 retrieval 解释。
topic extraction 默认使用 spaCy en_core_web_sm 抽英文 noun lemma。 不使用 spaCy；用中文可审计 tokenization，结合 topic/domains/user text。 这是语言适配，不是完整照搬 LD 源码。
long-term retrieval Chroma 候选召回 + topic overlap + time decay；默认 relevance_memory_number 较小。 默认 JSON 遍历所有 event memories，按 overlap × decay 排序；Chroma 可选。 当前工程保留 LD scoring 语义，但降低工程依赖和随机检索复杂度。
Chroma document 原版常把 topics 作为 document/key，summary 在 metadata。 JSON backend 直接保存 MemoryRecord；Chroma 可选时存 summary 并带 metadata。 当前工程优先可审计性，不追求 byte-level 复现。

5.3 Personas 对照

机制 LD-Agent 原版 当前工程 差异说明
user trait extraction 当前 user inquiry 可抽取 user trait，并参与当前/后续 persona bank。 每个 M0 completed turn 后，从 user_message 抽 user trait。 当前工程不让当前未完成 user turn 在检索前写入 memory，避免 probe 信息泄漏。
agent trait extraction 从 agent response 抽取 agent traits，影响后续 turns。 从 M0 answer 抽 agent trait，写入普通 persona memory。 只用 M0 answer，避免 M1/M2/M3 的关系性回答污染普通 agent traits。
NO_TRAIT 如果没有可抽取 trait，返回 NO_TRAIT，不写入。 保留同类过滤规则，并有 fallback。 当前工程需要关注 fallback traits 是否过泛。
persona window 原版 max_user_personas/max_agent_personas 默认逻辑存在特殊行为。 当前工程默认 max_user_personas=5、max_agent_personas=5。 当前工程更显式控制 persona 数量，避免 traits 无限制增长。

5.4 Generator / LoRA / benchmark 为什么没有进入当前工程

未采用部分 如果采用会带来什么变量 当前工程为什么排除
LD-Agent Generator prompt 不同 prompt shell 会改变模型如何使用记忆。 本实验要比较 M0/M1/M2/M3 memory payload，因此 responder 外壳应统一。
ChatGLM3 + ResponseGenerator LoRA 模型可能因为训练过 LD prompt 而更会读 memory。 会把 generator training 能力混入记忆 representation 结果。
EventSummary / PersonaExtraction LoRA summary 和 trait 质量受 LD 训练数据影响。 当前工程使用统一 LLM 或 fallback，且记录 writer/failure 状态。
MSC / CC 数据链路 开放域长期对话 benchmark 的 gold response、session 分布、评估指标会进入实验。 ReMem-RE 研究的是 controlled relational expectation probes，不是 MSC lexical overlap。
BLEU/ROUGE/Distinct 主指标 会奖励接近 gold response 的 lexical overlap。 当前实验关注隐含意图、情绪状态、共同语境、关系边界和陌生化错误。

5.5 当前工程对 LD-Agent 的准确表述范围

表述 是否准确 原因
